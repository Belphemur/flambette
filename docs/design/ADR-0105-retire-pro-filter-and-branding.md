# ADR-0105: The PRO filter and PRO branding are retired

Status: accepted (2026-11-26)
* Supersedes: ADR-0054 (in part)

## Context

ADR-0054 replaced the retired `proOnly` boolean with a three-value
`source` facet (`all | pro | new`) and kept the PRO corner chip on
recipe cards, plan rows and the detail sheet. The `pro` bucket selected
`meta.is_pro` — the Mealime subscription split baked into the frozen
catalog (ADR-0001) — and the badge marked those same recipes.

The subscription split is a Mealime commercial fact, not a cooking fact.
Flambette is an offline-first household planner around a frozen catalog;
there is no plan, no upsell and no subscription to surface, so "PRO"
tells the household nothing actionable about the food. The owner ruled
the branding out: keep the data, drop every UI/UX element.

## Decision

1. **`SourceFilter` loses `'pro'`** and becomes `'all' | 'new'`. The
   Source dropdown offers **All sources / New** with their per-bucket
   counts, exactly as before minus the PRO row. `matchesSource` loses
   its `is_pro` branch — the meta argument narrows to `{ id }`.
2. **Every PRO badge is removed**: the card's corner chip
   (`RecipeCard.vue`), the plan row's inline chip (`PlanTab.vue`) and
   the detail sheet's header chip (`RecipeDetail.vue`). The NEW badge
   keeps the retired badge's shape (slot, chip, type scale) and remains
   the only corner mark.
3. **The `proOnly` migration is retired, not redirected.**
   `legacyProOnlySource` is deleted and `normalizeSource` accepts only
   the offered values: an older peer, backup or persisted blob still
   carrying `proOnly` or `source: 'pro'` lands on `'all'` under the same
   drop-unknown rule as the diet ids and protein values. There is no
   meaning left to migrate into — a household that had PRO pinned gets
   the whole catalog, which is the honest default once the facet is gone.
4. **The data stays.** `is_pro` remains on `VariantMeta` and in
   `public/data/*.json` (ADR-0001: frozen field). Only the facet and the
   badges are gone, so a future re-introduction is a UI change, not a
   catalog regeneration.

## Consequences

- A device updating from a pre-ADR-0105 build with `source: 'pro'`
  persisted opens the Recipes tab on **All sources**. That is deliberate:
  the alternative (keeping the value, rendering it as All) would carry a
  spelling the type forbids, and a migration to `'new'` would invert the
  meaning.
- A room whose members run mixed builds converges on the current-build
  member when the older peer's `proOnly`/`'pro'` value arrives: the
  normalization drops it instead of adopting a facet the new UI cannot
  render.
- The filter-bar control count is unchanged (the Source dropdown keeps
  its slot), so the Pixel 7 no-orphan grid (ADR-0027 WS1) is untouched.
- The `Crown` icon leaves the Recipes tab; the lucide bundle (ADR-0029)
  is untouched otherwise.

## Alternatives considered

* **Keep the `pro` value but relabel it** (e.g. "Mealime") — rejected.
  The bucket's only content is the subscription flag; a relabel is the
  same branding under a quieter name, and the facet still narrows the
  grid along a line the household cannot act on.
* **Migrate `proOnly: true` to `source: 'all'` explicitly in a
  persistence migration** — rejected. `normalizeSource`'s unknown-value
  fallback already lands there; a second, PRO-specific branch would be
  dead weight with no observable difference (the coding-philosophy
  order: DRY first).
* **Keep the PRO badge, drop only the filter** — rejected. The badge is
  the branding the owner ruled out; a mark with no corresponding filter
  is also the worst of both worlds (a visible distinction the household
  cannot act on).

## Decision log (coding-philosophy: DRY > SOLID > KISS)

- **Drop-unknown beats migrate-in-place (DRY)**: one coercion point
  (`normalizeSource`) already owns inbound source values on all three
  paths (blob, backup, room); retiring the migration removes a function
  instead of adding a third spelling's worth of branches.
- **Keep `is_pro` in the data (KISS)**: the catalog is frozen and
  regenerated by scrape scripts; mutating it to please the UI would
  couple a presentation decision to a data pipeline, and a UI-only
  revert stays a UI-only change.
